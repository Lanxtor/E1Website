Branches für Szenarien und Änderungen.

In E1 ist ein Branch eine Arbeitskopie eines Teils des Designs eines Projekts. Ingenieure ändern ihn, während main bleibt, wie es ist, übernehmen die Änderungen aus main Wert für Wert, lösen Konflikte bei den Daten und auf der Zeichnung und spielen den Branch als eine Änderung zurück nach main, die sich als eine Änderung rückgängig machen lässt. Nutzen Sie Branches für Was-wäre-wenn-Fälle, Designänderungen, Änderungspakete und Inbetriebnahmeumfänge.

Branches

Einen Teil des Designs ändern, während main bleibt, wie es ist

In E1 enthält ein Branch einen gewählten Ausschnitt des Anlagenmodells; was Sie darin ändern, ändert den Branch, nicht das Hauptdesign des Projekts.

Starten Sie einen Branch von der Seite Branches des Projekts, aus dem Kontextmenü des Projekts oder indem Sie Objekte im Explorer oder in einem 2D-Bereich auswählen und Branch ▸ New branch… wählen. Eine Vorschau des Umfangs listet auf, was mit Ihrer Auswahl kommt und warum: Eine Pumpe bringt ihre Stutzen, ihre angeschlossenen Leitungen und den 2D-Bereich, in dem sie gezeichnet ist, als Editable mit, und ihren Eigentümer als Information. Ändern Sie eine Zeile auf Leave out oder Information, wo sie nicht gesperrt ist, und erstellen Sie den Branch.

Betreten Sie den Branch, und das ganze Projekt zeigt den Inhalt des Branches, mit einer Leiste, die sagt, dass Sie darin sind. Das Branch-Symbol markiert jedes Objekt und jeden 2D-Bereich, den er ändert. Objekte außerhalb des Branches sind grau und dort nicht änderbar. In einer Zeichnung legt Show main die aktuelle Version von main in Rosa darüber, sodass Sie genau sehen, was der Branch anders zeichnet, und Branches on this drawing zeigt jeden offenen Branch, der einen 2D-Bereich ändert, jeweils in seiner Farbe.

Manches gehört immer zu main: Das Ausgeben einer Revision, die Einstellungen des Projekts und die Bibliothek werden in einem Branch abgelehnt. Tag-Nummern werden zentral vergeben, sodass zwei Branches nie dieselbe Nummer vergeben. Ein Branch erweitert nie, was Sie in main ändern dürfen.

Konflikte

Aus main übernehmen und Konflikte lösen, Wert für Wert

In E1 übernimmt Pull from main die Änderungen aus main Wert für Wert in einen Branch; nur was beide Seiten unterschiedlich geändert haben, ist ein Konflikt.

Ändert jemand main im Umfang des Branches, läutet eine Glocke an der Karte des Branches und listet auf, was sich geändert hat und wer es geändert hat. Pull from main übernimmt alles, was main geändert hat und der Branch nicht. Ein Wert, den beide unterschiedlich geändert haben, steht unter Conflicts, nach Objekt gruppiert, mit Base, Main und Branch nebeneinander: Wählen Sie Keep mine, Take theirs oder tippen Sie einen Wert und Use value. Keep mine everywhere und Take theirs everywhere erledigen viele auf einmal.

Konflikte werden auch auf der Zeichnung gelöst. Ein Symbol, das beide Seiten verschoben haben, erscheint zweimal, Main in Blau und Branch in Orange, durch eine gestrichelte Linie verbunden: Klicken Sie auf das, das Sie behalten wollen. Status folgen derselben Regel: Wo main und der Branch beide einen Status geändert haben, schlägt E1 den niedrigeren vor, und eine in einem Branch gegebene Unterschrift ist nach einer späteren Änderung dort ungültig.

Prüfung

Prüfung vor main: Branch-Typen und Merge-Anfragen

In E1 hat jeder Branch einen Typ, der festlegt, ob er vor main eine Prüfung braucht und wie seine Konflikte und die Änderungen in main behandelt werden.

Jedes Projekt startet mit drei Branch-Typen: Working branch, Design change (reviewed) und Commissioning package. Ein Project administrator legt für jeden Typ Review before main, Four eyes, was nach dem Push geschieht (After push), wie Editing in main die Objekte des Branches behandelt (Mark, Warn oder Block) und eine Regel für grafische Konflikte fest. Ein Tag- oder Validierungskonflikt ist immer die Entscheidung einer Person.

Ein Branch, der eine Prüfung braucht, fordert sie mit Ask for review an. Die Prüfer finden die Merge-Anfrage in ihrer Inbox, und die Objekte zeigen währenddessen Under merge review. Ein Lead engineer genehmigt oder klickt auf Request changes… mit dem, was sich ändern soll; beim Vier-Augen-Prinzip kann der Autor seinen eigenen Branch nicht genehmigen. Alex genehmigt oder lehnt nie eine Merge-Anfrage ab: Das tut eine Person.

Für Anlagen mit einem Änderungsmanagement (MOC) hält ein geprüfter Branch jede Änderung vom Stand der Dokumentation getrennt, bis ein zweiter Ingenieur sie genehmigt hat, und hinterlässt ein Protokoll alles Geänderten. Das MOC-Verfahren selbst bleibt das Ihres Unternehmens.

Push

Als eine Änderung nach main pushen, mit Protokoll

In E1 bringt Push to main einen Branch als eine Änderung ins Projekt, und jeder Push hinterlässt ein Protokoll dessen, was er geändert hat.

Ein Lead engineer oder höher pusht, und seine Rolle muss jede Änderung im Branch erlauben. E1 lehnt einen Push ab, solange main im Umfang des Branches Änderungen hat, die noch nicht übernommen wurden, solange Konflikte offen sind oder solange eine geforderte Prüfung nicht genehmigt ist, sodass nichts in main unbemerkt überschrieben wird. Der Push landet als eine Änderung, Pushed branch…, im Verlauf von main, und Undo this change nimmt alles zurück.

Jeder Push eines Branches oder eines Inbetriebnahmepakets schreibt ein Push-Protokoll: sein Datum, wer gepusht hat, und jedes Objekt, das er erstellt, geändert oder gelöscht hat, mit jedem Feld vorher und nachher. Ein Protokoll wird vom Push selbst geschrieben und ändert sich nie. Nach dem Push bleibt der Branch offen und zählt ab dem, was er gepusht hat, oder wird geschlossen, wenn sein Typ es vorsieht.

Inbetriebnahme

Aus einem Branch herausgeschnittene Inbetriebnahmepakete

In E1 werden fertige Teile eines Branches zu Inbetriebnahmepaketen, die für sich nach main gehen, jedes mit seinen Terminen, seinem Leiter und seiner Beschreibung.

Auf der Karte eines Branches erstellt New commissioning package ein Paket. Zeichnen Sie im Branch mit Package boundary (Lasso, Rechteck oder Ellipse) um die Arbeit in einer Zeichnung und fügen Sie sie hinzu, oder klicken Sie mit der rechten Maustaste auf Objekte und wählen Sie Branch ▸ Add to commissioning package. Ein Rohr, das die Grenze verlässt, wird dort markiert, wo es sie kreuzt, und das Paket listet auf, was es noch braucht, etwa einen Bereich, den der Branch erstellt hat.

Geben Sie dem Paket seine Beschreibung, Priorität, das geplante Inbetriebnahmedatum, den Inbetriebnahmeleiter und wer es abnimmt. Mark ready schneidet es so, wie es ist, aus dem Branch heraus, dann wird es geprüft und allein nach main gepusht. Der Branch zählt für diese Objekte danach ab main, sodass sein nächster Pull keinen Konflikt hat und sein Push sie nicht wiederholt. Setzen Sie Commissioned on, sobald die darin enthaltene Anlage in Betrieb genommen ist. Branches und Pakete sind Objekte der Bibliotheksklassen Branch und Commissioning package, sodass sie Ihre eigenen Attribute tragen und in Abfragen erscheinen.

Überblick

Branches im Dashboard und Alex in einem Branch

In E1 zeigen das Dashboard Branches und der Tab Branches jedes Objekts, was wo geändert wird.

Dashboards → Branches zeigt offene Branches, die in Prüfung, ihr durchschnittliches Alter, offene Konflikte und Branches nach Status und Eigentümer. Der Tab Branches eines Objekts listet die offenen Branches auf, die es ändern dürfen, mit dem, was jeder bisher geändert hat. Eigentümer, eine Eigentümergruppe und ein Bearbeiter machen klar, wer für jeden Branch verantwortlich ist, und Access and sharing kann einen Branch auf die Personen beschränken, die ihn sehen sollen.

In einem Branch ändern Alex und gespeicherte Assistenten den Branch, nie main, und nur das, was Sie ändern dürfen. Eine von Alex vorgeschlagene Änderung kann mit Open as branch als Branch behalten werden, um sie zu prüfen, bevor etwas den Stand der Dokumentation erreicht.

Fragen

Fragen, die Ingenieure stellen.

Was ist ein Branch in E1?

Eine Arbeitskopie eines Teils des Designs eines Projekts. Sie ändern ihn, während main bleibt, wie es ist, übernehmen die Änderungen aus main und spielen ihn als eine Änderung nach main zurück, wenn er bereit ist.

Wofür kann ich Branches nutzen?

Was-wäre-wenn-Szenarien, Designänderungen, die eine Prüfung brauchen, Änderungspakete und Inbetriebnahmeumfänge. Jedes Projekt startet mit den Branch-Typen Working branch, Design change (reviewed) und Commissioning package.

Was passiert, wenn main und ein Branch denselben Wert ändern?

Pull from main listet ihn als Konflikt mit Base, Main und Branch nebeneinander auf. Sie wählen Keep mine, Take theirs oder tippen einen Wert. Ein Symbol, das beide verschoben haben, wird in der Zeichnung zweimal gezeigt, sodass Sie auf das klicken können, das Sie behalten wollen.

Wer kann einen Branch nach main pushen?

Ein Lead engineer oder höher, dessen Rolle jede Änderung im Branch erlaubt. Ein Push wird abgelehnt, solange main nicht übernommene Änderungen in seinem Umfang hat, solange Konflikte offen sind oder solange eine geforderte Prüfung nicht genehmigt ist.

Kann ich einen Push rückgängig machen?

Ja. Ein Push landet als eine Änderung im Verlauf von main, und Undo this change nimmt alles zurück. Sein Push-Protokoll bewahrt jede Änderung, die er gemacht hat, jedes Feld vorher und nachher.

Kann ich in einem Branch eine Revision herausgeben?

Nein. Das Ausgeben von Revisionen, die Einstellungen des Projekts und die Bibliothek werden in main geändert. Pushen Sie zuerst den Branch, und geben Sie dort die Revision heraus.

Was ist ein Inbetriebnahmepaket?

Ein Teil eines Branches, gesammelt durch Umzeichnen oder per Rechtsklick, mit seinen Terminen, seinem Leiter und seiner Beschreibung. Sobald es als bereit markiert und geprüft ist, wird es für sich nach main gepusht.
